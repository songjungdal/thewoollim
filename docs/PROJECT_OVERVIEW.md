## 2. 프로젝트 구조와 기술 스택

### 2-1. 큰 그림: 화면과 서버가 분리된 구조

```
[사용자 브라우저]
   │  ① 미리 만들어진 HTML/JS 화면을 받음 (Next.js 정적 export 결과물)
   │  ② 화면이 열린 뒤 브라우저가 직접 /api/*.php 를 호출해 데이터를 받음
   ▼
[웹 서버 (Apache로 추정, .htaccess 사용)]
   ├─ 정적 화면 파일 (Next.js 빌드 결과)
   └─ api/*.php  ──► MySQL/MariaDB (회원·후기·투표 등)
                 └─► api/data/*.json (파티·예약·장바구니·쿠폰 등 파일 저장)
                 └─► 외부 서비스: 토스페이먼츠, 포트원, 알리고, 카카오/네이버/구글
```

- `next.config.ts` 에 `output: "export"` 가 설정되어 있습니다. Next.js의 서버 기능 없이 **HTML 파일로 미리 만들어 올리는 방식**입니다.
- 그래서 페이지 대부분이 `"use client"`(브라우저에서 동작하는 화면)이고, 데이터는 화면이 열린 뒤 PHP API에서 받아옵니다.
- 웹 서버 설정 파일 `public/.htaccess` 에 Apache 문법(`RewriteRule`, `mod_headers`)이 쓰였습니다. 그래서 Apache 계열 서버로 추정합니다. 실제 서버 종류는 [코드상 확인 불가]입니다.
- `trailingSlash: true` 설정 때문에 모든 주소는 끝이 `/` 로 끝납니다(예: `/mypage/`).

### 2-4. 빌드·배포 관련 (참고용, 실행하지 않음)

- `npm run build` 앞에 `prebuild` 로 `scripts/sync-company.mjs` 가 실행됩니다. 운영 API에서 회사정보를 받아 `app/lib/company-snapshot.json` 에 저장하는 스크립트입니다(푸터 깜빡임 방지용).
- `app/sitemap.ts`: 빌드할 때 한 번 sitemap.xml을 만듭니다. 공개 페이지 7개와 모집 중인 파티 상세 페이지만 넣습니다.
- **빌드할 때 실제 파티 목록을 받아 정적 HTML 에 넣습니다** (`app/lib/buildParties.ts`). sitemap 과 같은 운영 API(`/api/parties.php`)를 읽기만 하고, 빌드 한 번에 한 번만 요청합니다.
  - 메인(`app/page.tsx`)과 파티 상세(`app/party/[id]/page.tsx`)가 이 목록을 화면 코드(`app/HomeClient.tsx`, `PartyClientView.tsx`)에 넘깁니다.
  - 받지 못하면 예시 파티를 넣지 않고 "불러오는 중"으로 만듭니다. 빌드 기록에 `[build-parties]` 줄로 결과가 남습니다.
  - 정적 HTML 의 파티 정보·신청 상태는 **마지막 빌드 시점** 기준입니다. 화면이 열린 뒤에는 지금처럼 실시간 데이터로 바뀝니다.
- `public/robots.txt`: 관리자 경로와 매칭 투표 경로는 검색 노출을 막습니다.
- `public/.htaccess`: HTML은 캐시하지 않고, JS/CSS는 1년 캐시합니다. 404 페이지 지정, OAuth 콜백 주소 연결 규칙이 있습니다.
- 운영 배포는 GitHub Actions 수동 워크플로(`.github/workflows/deploy.yml`)로 합니다. 빌드·검사 → 배포 계획(dry-run) → 백업 → 반영 → 상태 확인 순서이며, 자세한 절차와 설정 항목은 `docs/DEPLOYMENT.md` 에 있습니다.
  - 프론트엔드(`out/`)와 PHP API(`api/`)는 따로 배포할 수 있습니다.
  - 서버의 비밀 설정, 운영 데이터(`api/data/`), 세션, 업로드 이미지, `.htaccess` 는 배포가 덮어쓰거나 지우지 않도록 규칙(`scripts/deploy/*.rsync-filter`)으로 보호합니다.
  - 서버는 AWS EC2 이고 SSH 로 접속합니다(접속 계정 [민감정보 생략]). 접속 정보(서버 주소·키)는 GitHub 의 `production` 환경 Secret 에만 두며, `main` 브랜치의 배포 작업만 사용할 수 있습니다.
  - **배포 실행**: 서버에 접속하는 단계(배포 계획·실제 반영·백업 목록·되돌리기)는 GitHub 의 `production` 환경에서 `main` 브랜치로만 실행됩니다. 별도의 배포 승인 단계는 없어 대표·개발자가 각자 바로 실행할 수 있습니다. 실제 반영과 되돌리기는 잠금(`DEPLOY_UNLOCKED`)이 풀려 있어야 합니다. Claude Code 에 "배포해"라고 하면 plan 작업 로그를 확인해 정해진 조건(api 변경 목록 일치, 삭제 0건, 검사 통과, 같은 커밋)을 모두 만족할 때만 바로 반영하고, 아니면 멈춰서 보고합니다(`docs/DEPLOYMENT.md` 8장).
  - **코드 병합 규칙**: `main` 에는 PR 로만 병합합니다. 별도 승인은 필요 없습니다(`main` 브랜치 삭제·강제 push 는 막혀 있음).

  - "나중에 입력하기"를 누르면 그 브라우저 탭을 닫을 때까지는 이동시키지 않습니다.

### 3-2. 메인 `/` (`app/page.tsx` · `app/HomeClient.tsx`)

- 화면 코드는 `app/HomeClient.tsx` 이고, `app/page.tsx` 는 빌드할 때 실제 파티 목록을 받아 넘기고 검색엔진용 제목·설명·구조화 데이터를 넣습니다(2-4, 7-2 16번 참고).
- 파티를 하나도 받지 못한 동안(빌드 때 못 받았고 화면이 열린 뒤에도 아직 응답 전) 파티 카드 자리에 **"파티 일정을 불러오는 중입니다."** 가 나옵니다. 예시 파티는 보여주지 않습니다.
- 정적 HTML 에서는 **빌드 시점에 이미 시작한 파티**를 "모집종료"·"모집 종료된 파티"로 그리고 목록 뒤로 보냅니다(한국 시간 기준, `app/page.tsx` 가 계산해 넘김). 화면이 열린 뒤에는 지금처럼 브라우저 시각으로 다시 판단합니다.

위에서 아래로 다음 순서입니다.

1. **헤더**
   - 메뉴: 참여하기 · 현장스케치 · 후기게시판 · 실시간 참여자 · 파티 일정 · FAQ
   - 메뉴를 누르면 해당 섹션으로 부드럽게 스크롤합니다.
   - 로그인하면 장바구니 아이콘(개수 배지)과 "마이페이지"가 보입니다.
   - 화면 폭별 (`app/components/Header.tsx`): 로고 왼쪽 · 메뉴 오른쪽 배치입니다. **1024px 이상**은 메뉴를 펼쳐 한 줄로 보여주고(메뉴 이름이 두 줄로 깨지지 않음, 간격 1024px 24px · 1280px 이상 32px), **1024px 미만**(768~1023px 포함)은 햄버거 버튼으로 엽니다(768~1023px은 메뉴를 펼치기에 폭이 부족해 메뉴 이름이 두 줄로 깨졌던 것을 바꿈). 좌우 여백은 1024px 미만 24px, 이상 40px입니다.
2. **히어로 — 롤링 슬라이드** (`app/components/HeroSlider.tsx`, 슬라이드 1장 `HeroSlide.tsx`, 글자 톤 `heroTone.ts`)
   - **1번 브랜드 슬라이드(고정)**: 브랜드 이미지 + 메인 문구("세상을 울리는 / 새로운 연결, 어울림", 소개 2줄) + [어울림 매칭파티 신청하기 →](신청 섹션으로 부드럽게 스크롤)
   - **2~4번 파티 슬라이드(모집중 파티 최대 3개)**: 파티 이미지 + 배지(모집중 / 마감임박) → 파티명(최대 2줄) → 일시(한 줄, 예: "2026년 10월 23일 (금) 20:00") → 장소·주소(다음 줄) → [이 파티 신청하기 →]. 남은 자리(남 n석 · 여 n석)는 표시하지 않습니다(마감임박 배지 판단에만 사용). **이미지 전체와 버튼 모두 누르면 파티 상세**(`/party/{id}/`)로 이동합니다.
     - 어떤 파티가 나올지: 관리자가 [메인이미지] 탭에서 고른 파티 중 모집중인 것만 순서대로 → 3개가 안 되면(설정이 켜져 있으면) 날짜가 가까운 모집중 파티로 채웁니다. 모집중 = 행사 일시 전이고 남·여 중 한쪽이라도 자리가 남음, 마감임박 = 남·여 남은 자리 합계 3 이하.
     - 메인 전용 이미지가 없는 파티는 파티 대표이미지(`imageUrl`)를 흐리게 깐 배경 위에 원본 비율 그대로 보여주고, 글자는 흰색으로 고정합니다.
   - **넘김**: 6초마다 자동으로 넘어가고(겹쳐 사라지듯 1.2초), 보이는 이미지는 7초 동안 아주 천천히 확대됩니다(1 → 1.06). 브라우저 탭이 숨겨지면 멈춥니다. 휴대폰에서는 좌우로 밀어 넘길 수 있고(50px 이상), 10px 넘게 밀면 상세로 이동하지 않습니다. 기기에서 "동작 줄이기"를 켠 사람에게는 넘김·확대 없이 1번만 보입니다. 슬라이드가 1장뿐이면 넘김과 인디케이터가 없습니다.
   - **인디케이터**(진행 바, 누르면 그 슬라이드로 이동 + 6초 다시 시작): 모바일은 이미지 오른쪽 위 반투명 검정 캡슐 안 흰 바(어떤 이미지 위에서도 보임), PC는 오른쪽 아래(글자 톤에 따라 흰색/검정 계열 바, 활성 바는 터쿼이즈/진한 청록). PC 위치는 아래쪽 20~32px(화면 폭에 비례), 오른쪽 24px(1024px 이상 40px)로 문구 쪽 좌우 여백과 맞춥니다. 활성 바는 6초 동안 채워집니다.

PC(768px 이상)는 **16:9 비율**(높이 = 폭 × 9/16)이라 관리자 권장 PC 이미지(1920×1080)와 관리자 미리보기(1440×810)와 같은 비율이고, 16:9 이미지는 잘리지 않습니다(예전에는 화면 높이의 88%·최소 700px이라 폭에 따라 위아래나 좌우가 잘렸음). 글자 블록은 이미지 높이 안에서 세로 가운데, **왼쪽 시작선은 헤더 로고와 같습니다**(같은 최대 폭 1280px · 좌우 여백 24px / 1024px 이상 40px). 글자 크기·여백·버튼 크기는 화면 폭에 비례해 커지고 줄어듭니다(아래 5-2 "히어로 제목"). 브랜드 제목("세상을 울리는 / 새로운 연결, 어울림")과 소개글 2줄은 PC에서 **줄마다 한 줄로 고정**(중간에서 끊기지 않음)이고, 768~1920px에서 화면 왼쪽 절반 안에 들어옵니다. 파티명은 폭 10글자 크기(10em, 화면 왼쪽 절반 정도) 안에서 최대 2줄이라 긴 이름도 오른쪽 인물을 덮지 않습니다.
   - **이미지가 바뀌어 보이는 현상 방지**: 서버 응답(`/api/hero.php`)이 오기 전에는 이미지를 그리지 않고 같은 크기의 검은 화면으로 둡니다(관리자가 바꾼 이미지 대신 기본 이미지가 잠깐 보였다가 바뀌지 않도록). 응답이 오면 0.5초에 걸쳐 나타납니다. 지난 응답은 브라우저에 저장해 두었다가(`woollim_hero_slides`) 다음 방문 때 바로 보여주고, 서버 응답으로 최신화합니다. 응답이 실패하거나 5초 안에 오지 않으면 저장값을, 저장값도 없으면 기본 브랜드 1장(`hero-bg.webp`)을 보여줍니다. 검은 화면일 때도 검색엔진·화면낭독기용 제목은 숨겨서 넣어 둡니다.
   - 첫 슬라이드 이미지만 먼저 받고 나머지는 필요할 때 받습니다(다음 슬라이드는 미리 받음).

     - 쿠폰: 체크 표시 칩 2개("파티당 1매 사용", "다른 쿠폰과 중복 적용 불가")

     - 제휴: [협업 및 제휴문의 바로가기] 버튼(`/partnership`)
     - 환불: 시기별 환불 비율 막대(파티 5일 전까지 100%, 4일 전 80%, 3일 전 50%, 2일 전 ~ 당일 "환불 불가"는 빨간 글씨)

   - 내용은 `app/lib/data.ts` 의 `FAQS`(항목마다 질문 `q`, 한 줄 요약 `lead`, 설명 `body`, 선택 블록 `steps`·`refund`·`chips`·`link`)에 있습니다. 질문 버튼에는 펼침 상태(`aria-expanded`)와 답변 영역 연결(`aria-controls`)이 붙어 화면 낭독기에서도 읽힙니다.

### 3-3. 파티 상세 `/party/{id}/` (`app/party/[id]/PartyClientView.tsx`)

- **처음 받는 화면(정적 HTML)**: 빌드 때 받은 실제 파티 데이터에 이 번호가 있으면, 정적 HTML 에 파티 이름·소개·일시·장소·대상·참가비가 들어 있고 화면이 열린 뒤 실시간 값으로 바뀝니다(`app/party/[id]/page.tsx`).
- **불러오는 중 화면**: 빌드 데이터에 없는 번호(빌드 뒤 새로 만든 파티, 빈 번호)는 서버에서 파티 목록을 받기 전까지 헤더와 가운데 회전 아이콘만 보입니다. 푸터는 그리지 않습니다(짧은 로딩 화면 아래에 푸터가 보였다가 본문이 뜨면 사라지는 깜빡임 방지).
- **검색엔진용 정보**: 빌드 데이터가 있는 파티는 "파티이름 | 10월 17일(토) 성남 | 어울림 매칭파티(또는 솔로파티)" 형식의 제목(연도 없는 짧은 날짜 + 메인 분류 지역 `locationTag`, 지역이 없거나 "기타"면 장소 그대로), 같은 기준의 설명, canonical, 구조화 데이터(Event)가 들어갑니다. 본문과 Event 의 장소는 전체 주소 그대로입니다(`app/lib/partySeo.ts`). 데이터가 없는 번호는 검색 결과에 넣지 않도록(noindex) 표시합니다.
- **공유 썸네일**(카카오톡·SNS 링크 미리보기, `og:image`·`twitter:image`): 2026-10-22부터 **상단이미지**(`heroImageUrl`, 16:9)를 먼저 쓰고, 없으면 대표이미지(`imageUrl`), 둘 다 없으면 사이트 기본 이미지(`og-main.jpg`)입니다(`app/party/[id]/page.tsx`). 구조화 데이터(Event)의 이미지는 예전처럼 대표이미지입니다. 정적 HTML 에 빌드 때 들어가므로 관리자가 상단이미지를 바꾸면 **다음 배포부터** 공유 썸네일이 바뀝니다. 카카오톡은 한 번 읽은 미리보기를 한동안 저장해 두므로 바로 바뀌지 않을 수 있습니다[코드상 확인 불가 — 카카오 쪽 저장 기간].
- **"모집 종료" 판단 시점**: 상세의 모집 종료(행사 다음 날부터)는 화면이 열린 뒤 브라우저 날짜로 계산합니다. 정적 HTML 에는 종료 전 모습으로 들어갑니다.

**화면 구성** (2026-10-21 개편, 명세 `docs/specs/party-detail-relayout.md`) — 모든 화면 폭에서 가운데 한 단입니다(오른쪽 예약 카드 없음). 본문 폭: 모바일 좌우 16px 여백 / 태블릿 720px / PC 860px. ★ 표시는 관리자가 파티마다 바꿀 수 있는 영역입니다.

2. **상단이미지** (맨 위, 모서리 둥글게)

   - 솔로파티 기본 문구: MC 진행 단체 파티이며, 결제하면 [확정 대기 중]이 되고 운영진 확인 후 [참가 확정] 문자를 보낸다, 참가 확정 및 안내 문자는 확정 시점에 맞춰 순차적으로 발송된다고 안내합니다(명세 `docs/specs/party-solo-guide.md` 6-1. 마지막 문장은 2026-10-22 사용자 요청으로 "별도의 프로필 카드 작성은 필요 없습니다."에서 바뀜. 운영 솔로파티 #57·#58은 이 문구를 따로 저장하지 않아 기본 문구가 그대로 보임).
6. **참가 항목 선택** (참가 구성이 있는 솔로파티만, 모집 중일 때. `app/party/[id]/PartyOptionPicker.tsx`) — 모든 화면 폭에서 위 한 줄 요약 아래에 나옵니다.
   - "참가 항목 선택 \*"과 항목마다 선택 카드(모바일 1열, 640px 이상 2열). 카드 내용: 항목 이름, 포함 회차와 시각, 가격, 회차별 남은 자리.
     - 로그인한 회원: **내 성별 가격**과 내 성별 남은 자리("남은 자리 1부 1석"). 내 성별 기준으로 포함 회차 중 하나라도 차 있으면 회색 + 취소선 + "마감"이고 고를 수 없습니다.
     - 로그인하지 않은 경우: 남/여 가격과 남/여 남은 자리("1부 남1·여2")를 함께 보여주고, 남녀 모두 마감인 항목만 막습니다. 한쪽만 마감이면 "남성 마감"/"여성 마감"을 빨간 글씨로 표시합니다.
   - 고른 카드는 청록 테두리 + 체크 표시가 됩니다. 고르지 않고 [참가하기]나 [장바구니 담기]를 누르면 "참가 항목을 선택해주세요"를 띄웁니다.
   - 같은 파티가 다른 항목으로 장바구니에 있으면 "장바구니에 담긴 참가 항목(2부)을 1부+2부(으)로 바꿀까요?"를 묻고, 바꾸면 장바구니의 항목만 바뀝니다(파티당 한 줄).
7. ★ **소개글** (관리자가 파티마다 쓰는 상세페이지형 소개, 매칭·솔로 모두 가능, `detail.about`): 바로가기 탭 위에 나옵니다. 제목(기본 "파티 소개") 아래에 묶음마다 소제목 → 본문(줄바꿈 그대로, 글자로만) → 사진(아래 "사진 표시 규칙"). **묶음이 0개면 영역 전체가 없습니다.**
8. **바로가기 탭** — "실시간 참가자 / 신청방법 / 진행방식 / 유의사항" (2026-10-21 사용자 요청으로 신청방법을 진행방식 앞으로 — 본문 순서도 같음)
   - 화면 전체 폭 흰 띠(아래 1px 선). 스크롤하면 헤더 바로 아래에 붙어 따라옵니다(sticky). 지금 보고 있는 섹션의 탭이 굵게 + 밑줄입니다.
   - 탭(또는 이미지의 인원 표시)을 누르면 그 섹션 제목이 탭 바로 아래(16px 여백)에 오도록 부드럽게 이동하고, 주소 끝에 `#participants` 같은 이름이 붙습니다. 이 주소로 바로 들어와도 같은 위치로 이동합니다.
   - 모바일은 4칸 균등(359px 이하는 글자 13px, 글자 길이에 맞춰 나눔), 태블릿·PC는 가운데 정렬. 탭 이름은 줄바꿈되지 않습니다. 내용이 없는 섹션(예: 진행 단계 0개)의 탭은 나오지 않습니다.
9. **실시간 참가자 명단** (`app/party/[id]/ParticipantsRoster.tsx`, 30초마다·창으로 돌아올 때 새로 받음) — 신청자가 없어도 항상 보입니다.
   - 제목 "실시간 참가자 명단" 오른쪽에 "14:05 기준 · 자동 갱신"(초록 점, 마지막으로 받은 한국 시간).
   - 제목 아래 한 줄: "총 n명 신청 · {정원 합계}자리 중 {남은}자리 남았어요"(남은 자리 청록) / 0명이면 "모집을 시작했어요 · 첫 번째 참가자가 되어 보세요"(청록) / 전체 마감·모집 종료면 "모집이 마감됐어요"(빨강). 숫자는 이미지 인원 표시·버튼 마감 판단과 같은 실시간 결제 인원(`party_counts`) 기준입니다.
   - 남/여 두 열(모든 화면 폭, 열 높이는 따로). 열마다 맨 위 성별 카드: 흰 동그라미 안 ♂/♀ 아이콘, "남성"/"여성", "n/정원", 진행바, "잔여 N석"(다 차면 "마감"). 태블릿·PC는 이 카드가 한 줄입니다. 참가 구성 파티는 회차 자리를 모두 더한 값입니다(1부+2부 신청은 두 자리).
   - 그 아래 **실제 참가자 카드만** 신청 순서대로 한 장씩 세로로(빈자리 칸·점선 칸 없음). 카드 첫 줄은 이름(성만) + 상태 배지(참가확정 / 확정 대기 중 / 결제완료(프로필 대기) / 모임종료 — 마이페이지와 같은 색·모양). 공간이 모자라면 배지가 이름 아래 줄로 내려갑니다. 둘째 줄은 "연령대 · MBTI · 직업"(길면 …). 솔로파티는 연령대만(서버도 MBTI·직업을 빈 값으로 내려줌), 참가 구성 파티는 신청 항목 이름 배지가 붙습니다.
   - 이름은 서버(`api/party-participants.php`)가 **첫 글자 + 나머지 글자 수만큼 "\*"** 로 바꿔 보내고 원래 이름은 보내지 않습니다(김민준 → 김\*\*, 남궁민수 → 남\*\*\*, 한 글자 이름도 "김\*"). 화면도 같은 규칙으로 한 번 더 가립니다. 탈퇴 회원은 "\*\*\*". 명단 아래 범례·안내 문구는 없습니다.

11. ★ **참가 신청 방법** (`detail.apply`, 없으면 종류별 기본 문구): 단계마다 연회색 카드를 위에서 아래로(가로 배치·화살표 없음). 카드 왼쪽 검정 번호 동그라미, 오른쪽에 "STEP n"(작은 회색) · 제목 · 설명 · 참고가 있으면 카드 안 흰 상자(카드 안 설명과 같은 폭 — 2026-10-22 최대 640px 제한 없앰).
    - 매칭파티: 파티 카드를 확인하고 결제 → 프로필 카드 작성 → 파티 참가확정 확인 후 방문
    - 솔로파티: 파티 확인하고 결제하기 → 참가 확정 문자 확인하기 → 신분증 챙겨서 방문하기
    - **3단계 참고 상자(취소·환불 안내) 기본 문구가 바뀌었습니다(2026-10-21, 매칭·솔로 모두)**: "남녀 성비 미달 또는 주최 측의 사정으로 모임이 취소될 경우, 참가비는 100% 전액 환불 처리됩니다." 예전 문구("…100% 환불이나 쿠폰 적립 후 다음 모임 선확정 중 선택…")는 코드에서 모두 지웠습니다. 운영 데이터를 공개 API로 확인한 결과(2026-10-21, 파티 31건) 예전 문구를 따로 저장한 파티가 없어 저장 데이터 교체는 하지 않았습니다.

    - 자유 형식(번호 끔): 번호·STEP 없이 제목과 문구만, 블록 사이 구분선.

    - 솔로파티 7개: 신분증(본인·성인 확인), 드레스코드(편안한 캐주얼), 건강한 음주 매너, 서로를 존중하는 매너, 신청한 회차 시간 지키기, 노쇼, 촬영 안내. "신청한 회차 시간 지키기"는 참가 구성(회차)이 있는 파티에서만 나옵니다(없으면 6개).

### 3-16. 어울림 멤버십 `/membership/` (자동결제 심사용, 2026-10-22)

토스페이먼츠 자동결제(빌링) 심사를 위해 만든 상품 페이지와 카드 등록·첫 결제 흐름입니다. **메인·상단 메뉴·파티 화면에는 링크가 없고**, 주소로 직접 들어가야 합니다. 네 화면 모두 검색엔진 색인 제외(`noindex`)이고 사이트맵(`app/sitemap.ts`)에도 없습니다. 이번 단계는 **첫 결제까지만**이며, 멤버십으로 파티 예약하기·매월 자동결제(스케줄러)·재결제·카드 변경·관리자 화면은 아직 없습니다.

- **상단 안내 한 줄**(`app/membership/MembershipNotice.tsx`): 서버 키 설정 전이면 회색 "멤버십 결제는 준비 중입니다. 지금은 가입할 수 없습니다.", 테스트 모드면 연한 노랑 "테스트 결제 — 실제로 청구되지 않습니다". 운영 모드(live)가 되면 테스트 문구는 자동으로 사라집니다.
- **소개 `/membership/`**: 검정 첫 화면에 "어울림 멤버십", "월 99,000원", 설명(조건에 맞는 매칭파티·솔로파티를 추가 참가비 없이 신청), [멤버십 시작하기] → `/membership/join/`. 그 아래 회색 카드 3개(이용 규칙 / 결제 안내 / 해지·환불), 현장 사진 2장, 하단 검정 띠와 [멤버십 시작하기]. 사진은 `public/images/gallery/g1~g3.webp`(서로 다른 세 장. g5~g9는 g1~g4와 같은 사진이라 쓰지 않음).
- **가입 `/membership/join/`**: 로그인 필요(비로그인 → `/login/?redirect=/membership/join/` → 로그인 뒤 복귀). 결제 정보 카드(상품, 결제 금액 99,000원, 오늘 결제일, 다음 결제일). 필수 동의 3개(멤버십 이용약관 → `/terms/#membership`, 정기결제(자동결제) → [보기]를 누르면 아래에 요약이 펼쳐짐, 환불 규정 → `/refund/#membership`). 미리 체크되어 있지 않고, 3개를 모두 체크해야 [카드 등록하고 시작하기]가 켜집니다. 이미 이용 중이면 안내와 마이페이지 링크가 나오고 버튼은 꺼집니다.
- **카드 등록**: 토스 결제창 SDK v2 `TossPayments(클라이언트 키).payment({ customerKey }).requestBillingAuth({ method: "CARD", successUrl, failUrl, customerEmail, customerName })`. customerKey는 회원마다 한 번 만든 무작위 값(UUID)이고 개인정보가 들어가지 않습니다. 창을 닫거나 오류가 나면 실패 화면으로 갑니다.
- **결과 `/membership/success/`**: 서버가 ① customerKey가 로그인 회원의 값인지 확인(다르면 거부) ② 빌링키 발급 ③ 99,000원 결제("어울림 멤버십 (월간)")를 한 번에 처리합니다. 성공하면 결제 금액·카드사·끝 4자리·이용 기간·다음 결제일을 보여주고 [마이페이지에서 확인하기]. 새로고침하거나 여러 번 호출해도 이미 처리된 결과만 다시 보여주고 다시 결제하지 않습니다. 결제사 응답을 받지 못하면 "결제 결과를 아직 확인하지 못했습니다" + [다시 확인하기](같은 주문번호로 토스에 조회).
- **실패 `/membership/fail/`**: 토스 오류 코드를 쉬운 문구로 바꿔 보여주고(모르는 코드는 토스 메시지 그대로), 오류 코드, "결제가 이루어지지 않았다면 청구되지 않습니다.", [다시 시도] → 가입 화면, [멤버십 안내로 돌아가기].
- **규칙**: 회원당 이용 중인 멤버십 1건. 이용 기간 = 결제일 ~ 다음 결제일 전날, 다음 결제일 = 다음 달 같은 날(그날이 없으면 말일). 해지는 마이페이지(3-7). 테스트 모드에서 만든 멤버십은 `is_test=true` 로 표시하며 혜택을 주지 않습니다(혜택 기능 자체가 아직 없음).

## 4. 비즈니스 로직

### 4-1. 회원가입

**흐름**
1. **본인인증 버튼**
   - 포트원(다날) 본인인증 창이 뜹니다.
   - 서버(`api/auth/verify-identity.php`)가 인증 결과를 직접 다시 조회합니다.
   - 확인한 이름·성별·생년월일을 서버 세션에 30분간 보관합니다.
   - **만 19세 미만이면 여기서 가입이 막힙니다.**
2. **정보 입력**
   - 연락처: 01로 시작하는 10~11자리
   - 이메일: 아이디로 사용
   - 비밀번호: 8자 이상
   - 비밀번호 확인
   - 개인정보 수집·이용 동의: 필수
3. **가입 처리**(`api/register.php`)
   - 이름·성별·생년월일은 **본인인증 결과만 사용**합니다. 화면에서 보낸 값은 무시합니다.
   - 이메일이나 휴대폰 번호가 이미 있으면 가입을 거절합니다.
   - 테스트 계정 이메일(남성 a 계열·여성 b 계열 1~20번)로는 가입할 수 없습니다("사용할 수 없는 이메일입니다"). 테스트 계정은 관리자 [테스트 회원 만들기]로만 만듭니다. 일반 가입으로 만들어지면 알림 문자를 하나도 못 받고 프로필 핵심 정보 잠금도 풀리기 때문입니다.
   - 비밀번호는 암호화(bcrypt)해서 저장합니다.
   - 가입하면 바로 자동 로그인되고 메인으로 이동합니다. 혼인여부가 비어 있으므로 이어서 필수정보 입력 화면(`/onboarding/`)으로 안내됩니다.

**기획 시 알아둘 점**
- 이용약관 동의 항목은 따로 없습니다. 마케팅 수신 동의 같은 선택 동의도 없습니다.
- 개인정보 동의 체크는 **화면에서만 확인**합니다. 서버에 동의 기록이 남지 않습니다.
- 예전 문자 인증번호 발송·확인 API(`api/send-sms.php`, `api/verify-sms.php`)는 **사용 중지**했습니다(2026-10-14). 가입 과정에서 쓰지 않는데, 로그인 없이 아무 번호로나 유료 문자를 보낼 수 있어서 어떤 요청에도 문자 없이 "사용하지 않는 기능입니다"(410)만 돌려줍니다.

### 4-4. 파티 신청 (참가 자격 → 장바구니 → 결제)

**파티 정보**
- 관리자가 등록한 파티는 서버 파일 `api/data/parties.json` 에 저장됩니다.
- 예시(샘플) 파티 목록은 **삭제했습니다(2026-10-16)**. 파티 데이터는 빌드할 때(`app/lib/buildParties.ts`)와 화면이 열린 뒤(`app/lib/useParties.ts`) 모두 `/api/parties.php` 에서 받습니다. 둘 다 받지 못한 동안은 "불러오는 중"으로 표시합니다(3-2, 3-3 참고).
- 응답을 읽어 파티 정보로 바꾸는 규칙은 `app/lib/partyNormalize.ts` 한 곳에 있습니다(빌드·화면 공통).

- 파티 종류는 **매칭파티(`matching`)와 솔로파티(`solo`)** 두 가지입니다. 종류 값이 없는 예전 파티는 매칭파티로 봅니다(`app/lib/data.ts` `partyTypeOf`). 신청·결제·환불·참가 자격 규칙은 두 종류가 같습니다.

**참가 자격 검사** (`app/lib/eligibility.ts`)
- 나이: 파티에 최소·최대 나이가 있으면 만 나이로 검사합니다.
- 혼인여부: **"싱글" 파티에는 돌싱 회원이 신청할 수 없습니다.** "돌싱" 파티는 누구나 신청할 수 있습니다.
  - "싱글" 파티 = 혼인여부가 "싱글 전용"이거나 **대상별이 "싱글"**인 파티입니다. 그래서 혼인여부를 "돌싱 (싱글도 허용)"·"누구나 (모두 허용)"로 두어도 대상별이 "싱글"이면 돌싱 회원은 신청할 수 없습니다(2026-10-25 확인, 동작은 바꾸지 않음 — 명세 `docs/specs/party-request-tabs.md` 확인 결과 B).
- 정원: 남/여 정원을 따로 검사합니다. 내 성별 정원이 차면 "남성(여성) 마감"이 표시됩니다.
  - 서버도 같은 기준(관리자가 입력한 파티별 남/여 정원)으로 마감을 판단합니다. 정원 값이 없거나 0 이하이면 12명으로 봅니다. (`api/lib.php` `partyStockLimit`)
- 중복: 이미 신청한 파티는 다시 신청할 수 없습니다.

**가격 규칙** (`app/lib/data.ts` `priceForGender`, `api/lib.php`)
- 남성은 남성 참가비, 여성은 여성 참가비를 냅니다.
- 성별 참가비를 설정하지 않았으면 기본 참가비를 씁니다.
- 1인 1매입니다(수량 개념 없음).

**솔로파티 참가 구성 (회차·참가 항목)** — 명세 `docs/specs/party-options-solo.md`
- 솔로파티는 한 파티 안에 **회차**(예: 1부 19:00, 2부 21:30)를 두고, 회원이 **참가 항목**(예: 1부 / 2부 / 1부+2부)을 골라 결제하게 할 수 있습니다. 매칭파티와 참가 구성을 넣지 않은 솔로파티는 지금과 똑같이 동작합니다.
  - 회차: 이름, 시작 시각, 남/여 정원. 1~5개. 시작 시각 순서로 저장합니다(회차는 모두 행사 당일 자정 전에 시작).
  - 참가 항목: 이름, 포함 회차(1개 이상), 남/여 가격. 1~6개. 묶음(1부+2부) 가격도 직접 입력합니다(자동 합산 아님).
- **가격**: 고른 항목의 내 성별 가격을 냅니다. 쿠폰 할인도 고른 항목 가격 기준입니다.
- **정원**: 회차별로 따로 셉니다. 1부+2부 신청자는 1부·2부 정원을 **모두** 차지합니다. 항목에 포함된 회차 중 하나라도 내 성별 정원이 차 있으면 그 항목은 마감입니다.
  - 파티 신청 인원(남/여)은 계속 **사람 수**입니다(1부+2부 신청자도 1명).
- **항목을 고르지 않거나** 그 파티에 없는 항목으로 결제하려 하면 서버가 거절합니다("참가 항목을 선택해주세요."). 같은 파티는 항목이 달라도 한 번만 신청할 수 있습니다. 항목을 바꾸려면 기존 예약을 취소하고 다시 신청합니다(환불 규정 적용).
- **관리자 저장 규칙** (`api/lib.php` `sanitizePartyOptions`, `api/admin/parties.php`)
  - 이름은 20자 이하이고 회차끼리·항목끼리 겹치면 안 됩니다. 시작 시각은 `HH:MM`, 정원은 1~100명, 가격은 1원 이상입니다.
  - 저장할 때 대표 참가비는 항목 가격의 최솟값, 대표 정원은 회차 정원의 최댓값으로 맞추고, "일시" 글자 속 시각은 첫 회차 시작 시각으로 바꿉니다(시각이 없으면 뒤에 붙임). 정렬·달력·모집 종료 판단이 이 값을 씁니다.
  - **신청자가 있으면 막는 수정**(취소되지 않은 예약 기준, 입금 전 무통장 포함): 신청자가 있는 회차·항목 삭제, 신청자가 있는 항목의 포함 회차 변경, 회차 정원을 신청 인원보다 적게 변경, 참가 구성 전체 삭제(단일 가격 또는 매칭파티로 전환). 이름과 가격은 바꿀 수 있고, 가격 변경은 이후 결제부터 적용됩니다.
- 관리자 화면에서 입력하고(3-13 "파티 등록 창"), 회원은 파티 상세에서 항목을 골라 장바구니 → 결제합니다(3-3 "참가 항목 선택").
- **남은 자리·마감 계산** (명세 8-3, `app/lib/data.ts` `partyStockStatus` 한 곳에서 계산 — 메인 카드, 일정 섹션, 상세 페이지 신청 차단이 모두 이 결과를 씀)
  - 참가 구성 파티는 파티 단위 신청 인원·대표 정원으로 마감을 판단하지 **않습니다**(1부만·2부만 신청자가 섞이면 자리가 남았는데도 마감으로 보이기 때문).
  - 항목 마감(성별): 포함 회차 중 하나라도 그 성별 정원이 참 → 성별 마감: 그 성별로 고를 수 있는 항목이 없음 → 모집 마감: 남녀 모두 마감.
  - 마감 임박: 마감이 아니고, 어느 회차든 남은 자리(남+여)가 1~3석.
  - 예: 1부·2부 남 정원 각 2명, "1부" 1건·"2부" 2건이면 남성 마감이 아니고 "1부"만 고를 수 있습니다("2부"·"1부+2부"는 마감).
  - 참가 구성이 없는 파티는 기존 계산식(정원 − 신청 인원)을 그대로 씁니다.
- **장바구니**: 파티당 한 줄이고, 참가 구성 파티는 고른 항목(`optionId`)을 함께 저장합니다(`app/context/AuthContext.tsx` `addToCart`, `api/cart.php`).

**신청 흐름**
```
파티 상세 (참가 구성 파티는 항목 선택) [참가하기] → 장바구니 담김 → 마이페이지 장바구니에서 [결제]
→ /checkout/ (카드 또는 무통장) → 결제 완료 → 프로필 카드 작성 → 운영팀 승인 → 참가확정
(솔로파티는 결제 완료 → 운영팀 승인 → 참가확정. 프로필 카드 작성 단계 없음)
```

### 4-5. 예약 상태

| 상태값(코드) | 화면 표시 | 의미 | 다음 단계로 넘어가는 조건 |
|---|---|---|---|
| `vbank_pending` | 입금 확인 중 | 무통장 신청 후 입금 확인 전 | 관리자가 [결제확인] 클릭 |
| `paid_pending_profile` | 결제완료 | 결제는 끝났지만 프로필 카드 미작성 (매칭파티만) | 회원이 프로필 카드를 완성하면 자동 전환 |
| `pending_approval` | 확정 대기 중 | 운영팀이 성비·프로필을 검토하는 중 | 관리자가 [참가확정] 클릭 |
| `confirmed` | 참가확정 | 참가 최종 확정 | 관리자가 매칭 투표를 종료하면 자동 전환 |
| `completed` | 모임종료 | 파티가 끝남 | - |
| `cancel_requested` | 취소 요청 중 | 회원이 취소를 요청함 | 관리자가 [취소승인처리] 클릭 |
| `refund_completed` | 환불 완료 | 취소 요청이 승인됨 | - |
| `cancelled` | 취소됨 | 관리자가 취소함 | - |

```
카드결제 ──────────────┐
                       ├─(프로필 있음)→ 확정 대기 중 ─[참가확정]→ 참가확정 ─[투표종료]→ 모임종료
무통장 → 입금 확인 중 ─[결제확인]┤
                       └─(프로필 없음)→ 결제완료 ─(프로필 작성)→ 확정 대기 중
                         (솔로파티는 프로필과 상관없이 항상 위쪽 "확정 대기 중")
어느 단계에서든: 회원 [취소요청] → 취소 요청 중 → [취소승인처리] → 환불 완료
               관리자 [취소]/[100%환불] → 취소됨
```

- [참가확정]은 관리자 화면에서 확정 버튼이 보이는 상태(확정 대기 중, 결제완료(프로필 미작성))에서만 됩니다. 서버도 이미 참가확정·취소됨·취소 요청 중·환불 완료·모임종료·무통장 입금 대기 예약은 거절하고 상태와 문자를 바꾸지 않습니다(다른 관리자가 먼저 처리한 예약을 갱신 전 화면에서 눌러도 되돌아가거나 확정 문자가 다시 나가지 않음, `api/admin/bookings.php`).
- **상태는 예약마다 정합니다** (`api/payments/success.php`, `api/admin/bookings.php` `confirm_vbank`). 솔로파티 예약은 결제(무통장은 입금 확인) 즉시 `pending_approval`이고, 매칭파티 예약은 프로필(이름·성별·직업·MBTI) 완성 여부로 정합니다. 매칭파티와 솔로파티를 한 번에 결제하면 각 예약이 자기 규칙을 따릅니다. 파티 종류는 결제 시점의 파티 정보로 판단합니다.
  - 이 변경 전에 만들어진 솔로파티의 "결제완료" 예약은 그대로 두고, 관리자가 [참가확정]으로 바로 확정할 수 있습니다.

### 4-6. 결제

**카드·간편결제(토스페이먼츠)**
1. 결제 준비(`api/payments/pending.php`)
   - 서버가 금액을 다시 계산합니다(성별 참가비와 쿠폰).
   - **정원을 미리 확인합니다.** 내 성별의 현재 인원 + 1이 파티 정원을 넘으면 "정원이 마감되었습니다."로 거절하고, 결제창을 열지 않습니다. 장바구니에 파티가 여러 개면 파티마다 확인하고, 하나라도 마감이면 거절합니다.
   - 참가 구성이 있는 솔로파티는 고른 항목을 확인하고, 항목에 포함된 **모든 회차**를 내 성별 기준으로 미리 확인합니다.
   - 주문번호를 발급합니다. 이 주문은 **10분 동안 유효**합니다. 이때 계산한 줄별 가격을 주문에 저장해, 결제 도중 관리자가 가격을 바꿔도 예약 금액은 결제한 금액과 같게 남습니다.
2. 토스 결제창에서 결제합니다.
3. 결제 성공 처리(`api/payments/success.php`)
   - 서버가 기대한 금액과 실제 결제 금액이 같은지 확인합니다(위변조 방지).
   - 토스에 결제 승인을 요청합니다.
   - 파티별 정원 초과 여부를 다시 확인합니다(결제창에 있는 동안 마감됐을 수 있음). 참가 구성 예약은 포함 회차마다 확인하고, 결제 도중 고른 항목이 삭제·변경됐으면 "참가 항목 정보가 바뀌어 결제를 진행할 수 없습니다. 결제는 자동 취소되었습니다"로 자동 취소합니다.
     - 초과면 **토스 결제를 전액 자동 취소**합니다(사유 "정원 마감으로 자동 취소"). 예약은 만들지 않고, 쿠폰도 사용 처리하지 않으며, 기록을 남깁니다. 회원에게는 "정원이 마감되어 결제가 자동 취소되었습니다"를 보여줍니다.
     - 자동 취소마저 실패하면 긴급(CRITICAL) 기록(주문번호·토스 결제키 포함)을 남기고, 회원에게 "운영팀이 확인 후 환불해드립니다. 고객센터로 문의해주세요"라고 안내합니다. 이때는 운영팀이 직접 환불해야 합니다.
   - 쿠폰을 확인하고 사용 처리한 뒤, 신청 인원을 +1 합니다. 참가 구성 예약은 포함 회차의 인원도 각각 +1 합니다.
     - 토스 승인 뒤에 다음 이유로 실패해도 **토스 결제를 전액 자동 취소**합니다: 파티를 찾을 수 없음, 쿠폰 적용 불가 파티, 쿠폰 무효(꺼짐·만료), 성별 제한 쿠폰, 이미 사용한 쿠폰, 쿠폰 수량 소진, 쿠폰 사용 기록 파일을 열 수 없음(안내: "쿠폰 처리 중 오류가 발생했습니다. 결제는 자동 취소되었습니다").
     - 회원에게는 "(실패 사유). 결제는 자동 취소되었습니다"를 보여줍니다. 예: "이미 사용한 쿠폰입니다. 결제는 자동 취소되었습니다"
     - 취소가 실패하면 정원 마감 때와 같이 긴급 기록을 남기고 "(실패 사유). 결제 취소 처리 중 문제가 발생해 운영팀이 확인 후 환불해드립니다. 고객센터로 문의해주세요"라고 안내합니다.
     - 자동 취소 기록은 모두 `api/data/_counts_failure_alert.log` 에 남고, 관리자 대시보드 운영 현황 팝업의 시스템 오류 수(오늘 건수)에 포함됩니다(`api/admin/error-count.php`).
   - 예약을 생성하고 문자를 발송합니다. 참가 구성 예약에는 결제 당시의 항목 이름·포함 회차·회차 시작 시각을 함께 저장합니다(나중에 관리자가 항목 이름을 바꿔도 예약에는 결제 당시 이름이 남음). 단, **회차 시각은 파티의 현재 회차 시각을 따릅니다** — 관리자가 회차 시각을 바꾸면 안내 문자·2시간 전 안내·마이페이지에 바뀐 시각이 쓰이고, 회차를 찾지 못할 때만 저장해 둔 시각을 씁니다(`api/lib.php` `bookingSessionTimes`).
   - 장바구니에서 결제한 파티를 지웁니다.
4. 결제 완료 화면으로 이동합니다. 실패하면 `api/payments/fail.php` 를 거쳐 결제 화면으로 돌아갑니다.

**무통장 입금**
1. 입금 신청(`api/payments/vbank-submit.php`)
   - 카드와 같은 방식으로 정원을 미리 확인합니다. 마감이면 "정원이 마감되었습니다."로 거절합니다.
   - 상태가 "입금 확인 중"이 됩니다.
   - 쿠폰은 이 시점에 바로 사용 처리됩니다. 쿠폰 사용 기록 파일을 열 수 없으면 "일시적인 오류로 신청하지 못했습니다. 잠시 후 다시 시도해주세요."로 거절하고 예약을 만들지 않습니다(`api/payments/vbank-submit.php`).
   - **신청 인원 수에는 아직 넣지 않습니다.**
2. 회원이 운영사 계좌로 직접 입금합니다. 가상계좌가 아닙니다.
3. 관리자가 대시보드에서 [결제확인]을 누르고 **실제 입금액을 입력**합니다.
   - 이때 파티별 정원을 확인하고, 인원을 +1 하고, 상태를 바꾸고, 문자를 발송합니다. 정원이 찼으면 "잔여 정원을 초과하여 입금 확인을 진행할 수 없습니다."로 막습니다.
   - 참가 구성 예약은 신청 때 저장한 회차마다 정원을 확인하고(막히면 마감된 회차 이름을 함께 보여줌), 포함 회차 인원도 +1 합니다.

**쿠폰** (`api/coupons-validate.php`, `api/admin/coupons.php`, `api/lib.php`)
- 종류
  - 정액(원): 파티 가격을 넘지 않는 범위에서 할인합니다.
  - 정률(%): 최대 할인 금액을 정할 수 있습니다.
- 설정 항목: 적용 가능 성별, 총 사용 가능 수량, 만료일, 사용 여부
- 사용 제한
  - 한 회원은 같은 쿠폰을 한 번만 쓸 수 있습니다.
  - **결제 1건에 쿠폰 1장, 파티 1개에만 적용**됩니다.
  - **쿠폰 적용 불가 파티**(`parties.json`의 `couponDisabled: true`, 매칭·솔로 공통)에는 쓸 수 없습니다. 서버가 쿠폰 확인(`api/coupons-validate.php`), 카드 결제 준비(`pending.php`), 무통장 신청(`vbank-submit.php`)에서 "※해당 파티는 쿠폰 적용 대상이 아닙니다."로 거절합니다. 결제 준비 뒤 관리자가 설정을 켠 경우에는 카드 승인 뒤(`success.php`) 토스 결제를 전액 자동 취소합니다("※해당 파티는 쿠폰 적용 대상이 아닙니다. 결제는 자동 취소되었습니다"). 모두 쿠폰 사용 처리 전에 거절하므로 쿠폰은 소진되지 않습니다.
  - 이 안내 문구는 `api/coupon-messages.json` 한 곳에만 있고, 서버(`api/lib.php` `couponDisabledMessage()`)와 화면(`app/lib/data.ts` `COUPON_DISABLED_MESSAGE`)이 같은 파일을 씁니다.
- 할인 후 결제금액이 0원이 되면 결제가 거절됩니다. 그래서 100% 할인 쿠폰은 쓸 수 없는 구조입니다.
- 관리자가 취소하거나 환불하면 쿠폰을 다시 쓸 수 있게 돌려줍니다.

### 4-7. 취소·환불

**환불 규정** (`app/lib/refund.ts`, `/refund/` 페이지, 서버 `refundQuote()`(`api/lib.php`)에 같은 규칙 적용. 회원이 취소요청한 날 기준으로 계산)

| 파티까지 남은 날 | 환불 비율 |
|---|---|
| 5일 전 이상 | 100% |
| 4일 전 | 80% |
| 3일 전 | 50% |
| 2일 전 ~ 당일 | 환불 불가 |

- 남은 날은 **자정 기준**으로 셉니다. 환불액은 원 단위 이하를 버립니다.

**관리자 처리 방식** (`api/admin/bookings.php`)

| 버튼 | 결과 | 카드 결제 자동 취소 | 신청 인원 차감 | 문자 |
|---|---|---|---|---|
| [취소승인처리] (취소요청 탭) | 환불 완료 | ○ (규정 비율만큼) | **×** | × |
| [취소] | 취소됨 | **×** | ○ | ○ (취소 안내) |
| [100%환불] (카드만) | 취소됨 | ○ (전액) | ○ | ○ (전액 환불 안내) |

- 참가 구성 예약을 [취소]·[100%환불]하면 포함 회차의 인원도 함께 줄어듭니다. 환불액은 지금처럼 실제 결제액 기준입니다.
- 회원이 직접 부르던 예전 즉시 취소 API(`api/payments/refund.php`)는 막아 두었습니다. 어떤 요청에도 "취소는 마이페이지 [취소요청]으로 해주세요"(410)만 돌려줍니다.
- 관리자 [취소요청] 탭 상단 안내 상자에 처리 순서가 적혀 있습니다. [취소승인처리] 뒤에 [예약 / 신청 현황]에서 [취소]를 한 번 더 눌러야 인원이 줄고 취소 완료 문자가 나가는 **수동 2단계 운영**입니다. [취소]를 누른 건은 취소요청 탭 목록에서 사라집니다.
- [취소승인처리]는 **회원이 취소요청한 날 기준으로 저장된 금액**(`refundRequestAmount`)으로 환불합니다. 승인이 늦어져도 금액은 바뀌지 않습니다. 이 저장값이 없는 예전 요청은 요청 시각(`cancelRequestedAt`) 기준으로 같은 규정을 적용합니다. 금액이 0원이면 카드 결제 취소 없이 상태만 환불 완료로 바뀝니다.
- 취소요청 탭의 "환불받을 금액" 칸은 취소요청 건이면 요청일 기준 확정 금액, 환불 완료 건이면 실제 환불액을 보여줍니다.
- 무통장 환불은 시스템이 송금하지 않습니다. 운영자가 직접 송금하는 방식입니다. 회원의 환불 계좌를 입력받는 화면은 없습니다.

### 4-8. 자동 문자 알림

| 언제 | 내용(요약) | 파일 |
|---|---|---|
| "확정 대기 중"이 될 때 | 참가신청 완료. 성비 검토 후 참가확정 문자 예정 | `api/_pending_sms.php` |
| "결제완료(프로필 대기)"가 될 때 (매칭파티만. 솔로파티는 이 상태가 되지 않음) | 프로필 카드 작성 안내 | `api/_profile_notify_sms.php` |
| 결제완료 상태로 24시간이 지났을 때 | 프로필 작성 재안내 | `api/cron/profile_24h_reminder.php` |
| 관리자 [참가확정] | 참가확정 안내(일시·장소·복장·시간 엄수) | `api/admin/_confirm_sms.php` |
| 관리자 [취소] / [100%환불] | 취소 안내 / 전액 환불 안내 | `api/admin/_cancel_sms.php` |
| 파티 전날(KST 18시, 주석 기준) | 내일 파티 안내(신분증, 10분 전 도착) | `api/cron/d1_reminder.php` |
| 파티 시작 2시간 전 | 최종 안내(입장 시간, 대중교통 권장). **솔로파티 예약은 별도 문구**: 시작 시각 10분 전부터 입장, 늦어도 입장 가능, 신분증으로 본인·성인 확인, 술 파티라 대중교통 권장. 장문 제목 "[어울림] 솔로파티 시작 2시간 전 안내". 매칭파티 문구는 그대로 | `api/cron/start2h_reminder.php` |
| 비밀번호 찾기 | 임시 비밀번호 | `api/auth/reset-password.php` |

- **문자가 나가지 않는 경우**: 무통장 신청 접수, 회원 취소요청 접수, 관리자 [취소승인처리]
- 테스트 계정(남성 a 계열·여성 b 계열 **1~20번**)과 관리자 계정(관리자 권한, 관리자 전용 도메인)에는 발송하지 않습니다. 위 표의 모든 자동 문자가 `api/lib.php` 의 같은 규칙(`isSmsExcludedAccount` → `isTestUser`)을 쓰고, 임시 비밀번호 문자도 테스트 계정에는 보내지 않습니다(403). 번호 범위는 `api/lib.php` 와 `app/lib/testUsers.ts` 의 `TEST_USER_MAX`(현재 20) 두 곳만 고치면 바뀝니다. 90바이트를 넘는 문자는 장문(LMS)으로 보냅니다.
- 파티 전날 안내와 취소 안내 문자는 파티 종류에 맞춰 "매칭파티" 또는 "솔로파티"로 적습니다(장문 제목 포함). 두 이름은 글자 수가 같아서 단문/장문 구분은 달라지지 않습니다. (`api/cron/d1_reminder.php`, `api/admin/_cancel_sms.php`)
- **솔로파티 참가 구성 예약**은 신청 접수·참가확정·취소·전날·2시간 전 문자에 "참가: 1부+2부"처럼 항목 이름 한 줄이 들어가고, 시각은 **그 회원이 처음 참석하는 회차**의 현재 시각으로 적습니다(관리자가 회차 시각을 바꾸면 바뀐 시각). 2시간 전 안내도 예약마다 처음 참석하는 회차 기준으로 보냅니다(2부만 신청한 회원은 2부 시작 2시간 전, 1부+2부 신청자는 1부 기준으로 한 번). 솔로파티 2시간 전 문자의 입장 시각은 그 예약의 처음 참석 회차 시작 시각의 10분 전입니다(예: 1부 20:00 → "19:50부터 입장", 2부만 22:00 → "21:50부터 입장", 명세 `docs/specs/party-box-sms.md` 2장).
- `api/cron/` 의 자동 작업은 서버의 예약 작업(systemd 타이머 3개, 웹 서버 계정으로 실행)으로 돌아갑니다(2026-10-14 서버에서 읽기 전용으로 확인): 파티 전날 안내 매일 18:00(KST), 프로필 재안내 매시 정각, 2시간 전 안내 5분마다.
- **점검 기록** (2026-10-14, 서버 읽기 전용 확인): 서버의 문자 코드는 저장소와 같습니다. 2026-09-23 이전에는 참가확정 문자의 테스트 계정 제외가 일부 계정만 막아서 테스트 계정에 참가확정 문자 23건이 실제로 나갔습니다. 그 뒤로는 모든 문자 로그에서 테스트·관리자 계정 발송이 0건이고, 건너뜀 기록만 남습니다.
- 참가확정 문자에만 따로 제외되어 있던 개인 계정 1개는 코드에서 뺐습니다. 이제 9종 문자가 모두 같은 제외 규칙을 씁니다.
- 장문(LMS) 판단은 글자를 UTF-8 기준(한글 3바이트)으로 세서, 단문으로 갈 수 있는 짧은 문자(임시 비밀번호 등)도 장문으로 나갑니다. 비용만 조금 더 드는 문제라 그대로 두었습니다.

### 4-9. 매칭 투표

- 관리자가 현장에서 [투표시작] → [투표종료] 순서로 진행합니다. 자동 일정은 없습니다(`api/admin/matching.php`).
- 참가자는 다음을 입력합니다(`api/matching/vote.php`).
  - 본인 번호(1~99)
  - 마음에 드는 이성 번호. 화면은 최대 2개를 받고, 서버는 1~3개를 허용합니다.
- **서로를 선택한 이성끼리 매칭**됩니다. 매칭되면 서로의 이름·생년월일·연락처를 보여줍니다(`api/matching/results.php`).
- 투표를 종료하면 해당 파티의 "참가확정" 예약이 모두 "모임종료"로 바뀝니다.
- [초기화]를 누르면 투표 기록을 지우고 상태를 되돌립니다.
- **솔로파티는 매칭 투표가 없습니다.**
  - 서버는 솔로파티의 투표 시작, 투표, 결과 조회 요청을 "솔로파티는 매칭 투표가 없습니다."로 거절합니다(`api/admin/matching.php`, `api/matching/vote.php`, `api/matching/results.php`).
  - 참가자 투표 화면의 파티 목록에도 솔로파티는 나오지 않습니다(`api/matching/state.php`).
  - 솔로파티도 모임종료 처리(`end`, "참가확정" → "모임종료")와 되돌리기(`reset`)는 그대로 씁니다. 모임종료 때 담당자가 비어 있으면 누른 관리자 아이디를 담당자로 기록합니다.

- 밝은 배경 위 청록 글자는 `brand-point-ink` 를 씁니다. 어두운 배경(검정 헤더·푸터, 히어로, 다크 섹션) 위에서는 `brand-point` 를 그대로 씁니다.
- `brand-point` 배경 위의 글자는 **검정**입니다(흰 글자 쓰지 않음).
- 보조 설명용 회색 글자는 밝은 배경 위에서 **최소 회색 500**을 씁니다. 회색 300/400은 입력창 안내문구(placeholder), 비활성 상태, 어두운 배경 위에서만 씁니다.
- 예전에 화면마다 직접 적던 빨강(#FF2300, #CC0000, #9A3A47 등)은 `danger`, 파랑(#3A85D9, #4FACFE)은 `info` 로 통일했습니다.

**메인 히어로 글자 톤 규칙** (`app/components/heroTone.ts` 한 곳에서 관리)

슬라이드마다 PC·모바일 각각 글자 톤을 정합니다. "흰 글자"(`dark`) = 어두운 이미지용, "어두운 글자"(`light`) = 밝은 이미지용. 관리자 화면에서 자동(이미지 분석)으로 고르거나 직접 고릅니다.

| 항목 | 흰 글자 (어두운 이미지) | 어두운 글자 (밝은 이미지) |
|---|---|---|
| 오버레이 — 모바일 (아래쪽 60%) | 아래에서 위로 검정 85% → 45% → 투명 | 아래에서 위로 흰색 85% → 50% → 투명 |
| 오버레이 — PC | 왼쪽에서 오른쪽으로 검정 75% → 35% → 투명 (전체 폭) | 왼쪽에서 오른쪽으로 흰색 90% → 55% → 투명 (왼쪽 55% 영역) |
| 제목 / 본문 | 흰색 / 흰색 85% | `brand-black` / neutral-700 |
| 강조("어울림") | `brand-point` | `brand-point-ink` |
| 글자 그림자 | 있음(검정 50%, 8px) | 없음 |
| 버튼 | 검정 배경·흰 글자·흰 테두리 20%, hover 터쿼이즈 + 검정 글자 | 검정 배경·흰 글자, hover `brand-point-ink` + 흰 글자 |
| PC 인디케이터 | 흰색 30% 바, 활성 `brand-point` | 검정 15% 바, 활성 `brand-point-ink` |

- 배지는 톤과 상관없이 불투명 배경입니다: 모집중 = `brand-point` 배경 + 검정 글자, 마감임박 = 빨강(red-600) 배경 + 흰 글자.
- 모바일 인디케이터는 톤과 상관없이 반투명 검정 캡슐 안의 흰 바입니다.
- 톤이 바뀔 때 글자·배경색은 0.6초에 걸쳐 바뀝니다.
- 메인 전용 이미지가 없는 파티 슬라이드는 항상 "흰 글자"입니다(흐리고 어둡게 깐 배경 위).

### 5-2. 폰트

| 폰트 | 불러오는 곳 | 실제 적용 |
|---|---|---|
| Pretendard Variable | `app/layout.tsx` 에서 CDN(jsdelivr) 링크로 로드 | **[확인 필요]** 아래 설명 참고 |
| Gaegu(손글씨체) | `app/globals.css` 에서 Google Fonts로 로드 | 관리자 메모에만 쓰려던 것으로 보임. 적용 여부 **[확인 필요]** |

- **Pretendard**: 화면 전체가 `font-sans` 를 쓰는데, 이것이 Pretendard를 가리키도록 설정된 곳이 코드에 없습니다. 그래서 **실제로는 기기 기본 글꼴(시스템 폰트)로 보일 가능성**이 있습니다. Pretendard를 직접 지정한 곳은 오류 화면(`app/global-error.tsx`) 한 곳뿐입니다. 실제 화면은 브라우저에서 확인해야 합니다.
- **Gaegu**: 쓰는 클래스(`font-gaegu`)가 로드되지 않는 `tailwind.config.js` 에만 정의되어 있어서, 실제로 적용되지 않을 수 있습니다.
- **글자 굵기**: 굵게(bold)와 아주 굵게(black)를 많이 씁니다. 대비가 강한 톤입니다.
- **글자 크기**: 본문은 작은 크기(text-sm 14px, text-xs 12px)가 가장 많습니다.
  - 사용자 화면의 **최소 글자 크기는 12px**(text-xs)입니다. 예전에 배지 등에 쓰던 9~11px은 모두 12px로 올렸습니다.
  - 파티 상세·마이페이지·결제·프로필 카드에서 본문 성격의 작은 안내글은 **모바일에서 13px**로 키웠습니다(PC 크기는 그대로).
  - 관리자 화면(`/admin****`, 투표 관리)은 최소 11px입니다.
  - 입력창 글자는 모바일에서 16px 이상입니다(아래 5-3 참고).
- **제목 패턴**
  - 섹션 제목: 모바일 text-4xl, PC text-6xl, 굵게
  - 히어로 제목: 모바일 28px(파티명 25.6px). PC는 화면 폭에 비례 — 브랜드 제목 40~80px(폭의 5%, 1440px에서 72px), 파티명 36~68px(폭의 4.4%), 소개글 15~20px(폭의 1.35%), 파티 일시·장소 14~20px, 버튼 글자 15~18px. 아주 굵게, 자간 좁게. 관리자 미리보기(PC)는 같은 값을 폭 1440px 기준으로 계산해 그립니다(`app/components/HeroSlide.tsx`).
- **한글 줄바꿈**: 단어 단위로 줄을 바꾸는 `break-keep` 을 자주 씁니다.

### 5-3. 반응형 구조

- **모바일 우선 + 768px(`md:`) 한 지점에서 PC로 전환**하는 구조입니다.
  - `md:` 접두사 사용 약 1,200회
  - `sm:`(640px) 약 26회, `lg:`·`xl:` 몇 회
  - 사실상 "모바일 / PC" 2단계 디자인입니다.
- **콘텐츠 최대 폭**
  - 본문·후기·약관: max-w-4xl(896px)
  - 헤더·푸터·메인 섹션: max-w-7xl(1280px)
  - 모달: max-w-md(448px)
- **섹션 여백**: 모바일 위아래 64px·좌우 16px, PC 위아래 128px·좌우 24px (`py-16 md:py-32 px-4 md:px-6`)
- **헤더**: 화면 위에 고정됩니다. 검정 배경입니다. 헤더는 768px이 아니라 **1024px(`lg:`)에서 전환**합니다 — 1024px 미만은 높이 72px + 햄버거 메뉴, 1024px 이상은 높이 96px + 펼친 메뉴(3-2의 1번).
- **메인 히어로**: 모바일은 4:5, PC(768px 이상)는 16:9 비율입니다(3-2의 2번).
  - 점검(2026-10-13, 로컬 화면): 360 / 390 / 430px은 바꾸기 전과 헤더·히어로(메뉴 열림, 파티 슬라이드 포함) 요소 위치·크기가 같습니다. 768 / 1024 / 1280 / 1440 / 1920px에서 히어로 16:9, 브랜드 제목·소개글 줄마다 한 줄, 문구 시작선 = 로고 시작선, 메뉴 한 줄(로그인 상태 포함, 768~1023px은 햄버거), 가로 스크롤 없음. 관리자 메인이미지 탭 PC 미리보기도 1440px 실제 화면과 글자 크기·버튼·인디케이터 위치가 같습니다.
- **푸터**: 모바일 2열, 큰 화면(1024px 이상) 4열입니다.
- **하단 고정 버튼 바**: 회원 화면에서는 **파티 상세페이지에만** 있습니다(2026-10-21, 3-3의 17번). 높이 모바일 68px / 태블릿 76px / PC 88px이고 본문 아래에 같은 높이의 여백을 둡니다. 아이폰 홈 표시줄 여백(`env(safe-area-inset-bottom)`)을 더하도록 적었지만, 사이트 전체가 `viewport-fit=cover`를 쓰지 않아 이 값은 0으로 계산되고 여백은 브라우저가 알아서 둡니다(전체 설정은 바꾸지 않음 — 실제 아이폰에서 확인 필요). 관리자 화면에는 모바일에서만 [신규 등록] 버튼과 파티 등록 창 아래 버튼 바가 고정됩니다(아래 "관리자 화면 시인성·모바일 규칙").
- **파티 상세페이지 반응형 기준** (2026-10-21, 명세 `docs/specs/party-detail-relayout.md` F장 — Tailwind `md` 768px / `lg` 1024px)
  - 모바일(~767px): 본문 좌우 여백 16px. 정보 패널은 라벨 숨김·값 한 줄, 하단 바는 모바일형, 사진 2장 이상은 옆으로 넘겨 보기, 참가자 명단 남/여 2열 유지. 섹션 제목 20px, 본문 14px.
  - 작은 폰(~359px): 하단 바 제목 13px·일시/장소 11px, 바로가기 탭 13px(탭 이름 줄바꿈 없음), 이미지 인원 표시 11px, 정보 패널 값 13px·일시 15px·금액 16px, 참가자 이름 13px(상태 배지는 이름 아래 줄로 내려갈 수 있음).
  - 태블릿(768~1023px): 본문 720px 가운데(좌우 24px), 상단 메뉴는 햄버거 그대로. 정보 패널 라벨 표시, 하단 바는 태블릿형, 사진 2장 이상은 2열. 제목 30px, 섹션 제목 24px, 본문 15px.
  - PC(1024px~): 본문 860px 가운데. 하단 바는 PC형(가운데 참가비 칸). 제목 36px, 섹션 제목 26px, 본문 15px(줄 간격 1.7), 섹션 사이 64px.
  - 공통: 가로 스크롤 없음(긴 주소·제목은 … 또는 줄바꿈), 바로가기 탭은 헤더 바로 아래(모바일·태블릿 73px / PC 97px)에 붙고, 앵커 이동 위치는 헤더+탭의 실제 높이를 재서 정합니다. 320 / 375 / 767 / 768 / 1023 / 1024 / 1280px에서 가짜 데이터로 확인했습니다(2026-10-21).
- **메인 일정 섹션**: 화면 폭에 따라 **세 가지 형태**입니다(자세한 내용은 3-2의 6번).
  - PC(1024px 이상): 달력(약 65%) + 오른쪽 상세 패널(약 35%, 화면에 고정)
  - 태블릿(768~1023px): 전체 너비 달력 + 아래 상세 패널
  - 모바일(768px 미만): 작은 달력(칸 높이 48px) + 날짜별 일정 리스트

**모바일 화면 기준** (2026-10-09 점검: 360px / 390px / 430px 폭)
- 점검한 화면: 메인, 헤더, 푸터, 파티 상세, 결제, 마이페이지, 프로필 카드, 온보딩, 로그인·회원가입, 매칭 투표·결과. 세 폭 모두 **가로 스크롤이 생기지 않습니다**.
- **수정 원칙**: 모바일 기본 스타일에 `sm:`/`md:` 접두사를 붙여서만 조정합니다. **768px 이상(PC) 화면 결과는 바뀌지 않게** 합니다.
- **터치 영역 최소 44×44px**: 작은 아이콘 버튼(닫기 X, 삭제, 체크박스)과 글자 링크(뒤로 가기, 푸터 링크, 아이디·비밀번호 찾기, 취소요청·회원탈퇴 등)는 **보이는 모양은 그대로 두고 눌리는 영역만** 넓힙니다.
  - 방법 1: 안쪽 여백을 늘리고 같은 크기의 음수 바깥 여백으로 상쇄 (예: `p-[11px] -m-[11px]`, `py-3 -my-3`)
  - 방법 2: 보이지 않는 가상 요소로 눌리는 영역 확장 (예: `relative before:absolute before:-inset-1.5`) — 갤러리 페이지 점, 파티 카드 [신청하기], 마이페이지 삭제 버튼
  - 모바일 햄버거 버튼은 44×44px, 모바일 메뉴 항목도 각각 44px 높이입니다.
- **입력창 글자는 모바일에서 16px 이상**: 16px보다 작으면 아이폰에서 입력할 때 화면이 자동으로 확대됩니다. 모바일 16px, PC 14px(`text-base md:text-sm`)로 씁니다.
- **모달**: 모바일에서 화면보다 길어지면 패널 안에서 스크롤됩니다(`max-h-[90vh] overflow-y-auto`, PC는 예전과 같음).
- **좁은 화면의 2열 → 1열**: 결제 화면의 결제 수단 선택 카드(신용카드/간편결제 · 무통장 입금)는 640px 미만에서 1열, 이상에서 2열입니다.
