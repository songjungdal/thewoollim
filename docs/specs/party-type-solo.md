## 1. 작업 목적

MC가 진행하는 단체형 **솔로파티**를 새로 운영한다. 이를 위해 다음을 만든다.

1. 관리자가 파티를 등록할 때 **파티 종류(매칭파티 / 솔로파티)** 를 고른다.
2. 상세페이지의 **진행 안내와 사진을 파티마다 관리자가 직접 넣고, 빼고, 고칠 수 있게** 한다. 매칭파티와 솔로파티 모두 해당된다.
3. 메인 화면, 안내 문자, 현장 운영 도구, 법적 문서가 종류에 맞게 동작하도록 고친다.

## 2. 운영 방식 (운영자 확정, 2026-10-09)

| 항목 | 매칭파티 (기존) | 솔로파티 (신규) |
|---|---|---|
| 현장 진행 | 1:1 로테이션 대화 + 최종 매칭 투표 | **MC 진행 단체형, 매칭 투표 없음** |
| 신청 절차 | 결제 → 프로필 카드 → 운영팀 승인 → 참가확정 | **매칭파티와 동일** |
| 성별 정원 | 현재 6~12명으로 운영 | **12명 초과 가능** |
| 메인 노출 | 기존 신청 섹션 | **기존 신청 섹션 안에 종류 탭 [전체 / 매칭파티 / 솔로파티]** |
| 상세 진행 안내·사진 | 지금 코드에 고정된 내용 | **파티마다 관리자가 직접 편집** (둘 다) |
| 신규 등록 시 기본 내용 | 지금 매칭파티 내용 그대로 | **비어 있음** (관리자가 입력) |
| 환불 규정 | 5일 전 100% / 4일 전 80% / 3일 전 50% / 2일 전~당일 불가 | **동일 적용** |
| 법적 문서·동의문 | "매칭파티"만 적혀 있음 | **솔로파티를 포함하도록 수정** |
| 메인 신청 섹션 부제 | "돌싱부터 싱글까지, 원하는 테마와 지역을 선택하여…" | **바꾸지 않음** |

## 3. 현재 구조 (코드 확인 결과)

### 3-1. 파티 데이터
- 파티는 DB가 아니라 서버 파일 `api/data/parties.json`에 저장된다. 항목을 추가해도 DB 마이그레이션은 필요 없다.
- 관리자 등록 폼에는 분류 3종이 이미 있다(`targetGroup`, `theme`, `locationTag`). 모두 매칭파티 안에서 나누는 기준이고, 행사 종류를 구분하는 값은 없다.
- `tag` 필드는 화면 어디에도 쓰이지 않는 옛 값이다. 재활용하지 않는다.
- 운영 파티: 17건(공개 API 기준). 가장 큰 id는 56이다.
- 메인 화면은 `/api/parties.php`를 **10초마다** 다시 불러온다(`app/lib/useParties.ts`). 그래서 목록 응답에는 큰 데이터를 넣지 않는다.

### 3-2. 상세페이지에 고정된 진행 안내·사진 (`app/party/[id]/PartyClientView.tsx`)

| 위치 | 지금 들어 있는 것 |
|---|---|
| ① 참가 신청 방법 위 | `party_apply_guide_head.png` |
| ② 참가 신청 방법 아래 | `page_a01.webp` (현장 프로필 카드 작성 장면) |
| ③ 진행 안내 위 | `party_our_experience.webp`, `page_a02.webp`, `page_a03.webp` (1:1 로테이션 테이블 장면) |
| 진행 안내 (Party Timeline) | 제목·소개 문구, 4단계(입장 → 매칭카드 작성 → 1:1 로테이션 → 최종 매칭), 인원별 소요시간 3줄(6:6 / 8:8 / 10:10) |
| ④ 필수 확인 사항 위 | `page_a04.webp` ("MATCHING CHOICE" 투표 안내지) |
| ⑤ 필수 확인 사항 아래 | `page_a05.webp`, `party_required_notice_bottom.png` |

### 3-3. 위험 요소 (솔로파티 전에 해결 필요)
1. **서버 정원 12명 고정.** `api/payments/success.php`와 `api/admin/bookings.php`(무통장 입금 확인)가 `$STOCK_PER_SIDE = 12`로 마감을 판단한다.
   - 카드 결제는 **토스 승인 뒤에** 정원을 검사한다. 그래서 정원 초과로 실패하면 결제는 승인된 채로 남고, 자동 취소 코드는 없다.
2. **상세페이지는 id 1~100번만 미리 만들어진다**(`app/party/[id]/page.tsx`). `public/.htaccess`에도 대신 연결하는 규칙이 없다. 그래서 101번 이후 파티는 상세페이지가 404로 뜬다.

## 4. 데이터 설계

### 4-1. 파티 종류
- 새 필드: `partyType: "matching" | "solo"`
  - 저장값은 영문 코드, 화면에는 라벨을 쓴다(매칭파티 / 솔로파티).
- **값이 없거나 허용 목록에 없으면 `matching`으로 본다.** 기존 파티는 데이터 변환 없이 매칭파티가 된다. `parties.json`을 직접 고치지 않는다.
- 공통 정의는 두 곳에만 둔다.
  - `app/lib/data.ts`: `PARTY_TYPES`, `PartyType`, `PARTY_TYPE_LABELS`, `partyTypeOf(party)`
  - `api/lib.php`: `partyTypeOf(array $party): string`, `partyTypeLabel(array $party): string`

### 4-2. 상세페이지 안내 (`detail`) — 파티마다 저장

```ts
type PartyDetailImage = { url: string; alt: string };
type PartyDetail = {
  timeline: {
    title: string;   // 기본 "Party Timeline"
    intro: string;   // 기본 "편안한 분위기 속에서, 자연스럽게 이어지는 인연의 시작"
    steps: { title: string; time: string; desc: string; note: string }[];
  };
  durations: {
    title: string;   // 기본 "인원별 소요 시간 안내"
    rows: { label: string; total: string }[];
  };
  images: {
    beforeApply: PartyDetailImage[];     // ① 참가 신청 방법 위
    afterApply: PartyDetailImage[];      // ② 참가 신청 방법 아래
    beforeTimeline: PartyDetailImage[];  // ③ 진행 안내 위
    beforeNotice: PartyDetailImage[];    // ④ 필수 확인 사항 위
    afterNotice: PartyDetailImage[];     // ⑤ 필수 확인 사항 아래
  };
};
```

**기본 내용(템플릿)**
- 위치: `app/lib/partyDetailTemplates.ts` 한 곳
  - `MATCHING_TEMPLATE`: 3-2 표의 **현재 문구·사진·순서를 글자 하나 다르지 않게** 옮긴다. 대체 텍스트(alt)도 지금 값을 그대로 쓴다.
  - `SOLO_TEMPLATE`: 모두 비어 있다(단계 0개, 소요시간 0줄, 사진 0장). 제목 필드 기본값만 채운다.
- 이 템플릿은 상세페이지 화면과 관리자 편집기가 같이 쓴다.

**저장 규칙**
- 파티에 `detail`이 없으면 종류별 템플릿으로 보여준다.
  - 기존 매칭파티 17건은 따로 손대지 않아도 지금과 똑같이 보인다.
- 관리자가 그 파티를 저장하면 편집기에 있던 내용이 그 파티의 `detail`로 저장된다. 이후에는 그 파티 전용 내용이 된다.

**입력 제한** (서버에서 강제한다. 넘치면 저장을 거절하고 이유를 알려준다)

| 항목 | 최대 |
|---|---|
| 진행 안내 제목 / 소요시간 제목 | 60자 |
| 소개 문구 | 200자 |
| 단계 수 | 10개 |
| 단계 제목 | 60자 |
| 단계 소요시간 | 20자 |
| 단계 설명 | 500자 |
| 단계 참고 문구 | 200자 |
| 소요시간 줄 수 | 6줄 |
| 소요시간 구분 / 시간 | 각 30자 |
| 슬롯당 사진 | 10장 |
| 사진 대체 텍스트 | 100자 |

**사진 주소 허용 규칙**
- `/uploads/parties/파일명` 또는 `/images/파일명` 형태만 허용한다(정규식 `^/(uploads/parties|images)/[A-Za-z0-9._-]+$`).
- 외부 주소는 받지 않는다.

**보안**
- 모든 글은 일반 텍스트로만 보여준다(HTML 해석 없음). 제어문자는 서버에서 제거한다.
- 단계 설명과 참고 문구의 줄바꿈은 화면에 그대로 반영한다(`whitespace-pre-line`). 지금 매칭파티 문구에는 줄바꿈이 없으므로 화면이 달라지지 않는다.

## 5. 작업 내용

### A. [필수 · 선행 · 결제 영향] 서버 정원 검사를 파티별 정원 기준으로 변경

> 결제 흐름을 건드리므로 **별도 PR**로 진행하고, 토스 테스트 키 환경에서 검증한 뒤 배포한다.

**A-1. `api/payments/success.php`**
- `$STOCK_PER_SIDE = 12`를 파티별 상한으로 바꾼다.
  - 상한값은 `$partyMap[$pid]`의 `maleStock` 또는 `femaleStock`이다.
  - 값이 없거나 0 이하면 12를 쓴다.

**A-2. `api/admin/bookings.php` (`confirm_vbank`)**
- A-1과 같은 규칙을 적용한다.
- 이 블록은 지금 `parties.json`을 읽지 않으므로, 읽는 코드를 추가한다.

**A-3. 결제창을 열기 전에 미리 검사**
- 대상: `api/payments/pending.php`, `api/payments/vbank-submit.php`
- 현재 인원 + 1이 상한을 넘으면 `jsonFail('정원이 마감되었습니다.')`로 거절한다.
- 장바구니에 여러 파티가 있으면 회원 성별 기준으로 파티마다 검사한다.

**A-4. 토스 승인 뒤 정원 초과가 확인되면 자동 취소**
- 위치: `api/payments/success.php`의 `$soldOut` 분기
- 토스 결제를 전액 취소한다. 사유는 "정원 마감으로 자동 취소"로 한다.
- 취소 코드는 `api/admin/bookings.php`의 토스 취소 호출 방식을 그대로 쓴다.
- `_counts_failure_alert.log`에 기록한다.
- 회원에게는 "정원이 마감되어 결제가 자동 취소되었습니다"를 안내한다.
- 자동 취소가 실패하면 `CRITICAL` 로그를 남긴다.
- 참고: 지금 코드에서는 쿠폰 사용 처리가 정원 검사보다 뒤에 있다. 그래서 이 분기에서 쿠폰을 되돌릴 필요는 없다. 구현할 때 순서가 그대로인지 다시 확인한다.

**A-5. 기존 매칭파티에 생기는 변화**
- 회원 화면은 이미 파티별 정원으로 마감을 표시하고 있다. 따라서 회원이 느끼는 변화는 없다.
- 이번 변경 후에는 서버도 화면과 같은 기준으로 막는다.

### B. 파티 종류 저장·조회

**B-1. `api/admin/parties.php`**
- `sanitizeParty()`에 `partyType`을 허용 목록 방식으로 추가한다. 허용 목록에 없는 값은 `matching`으로 저장한다.
- `create`: `partyType`이 없거나 허용 목록 밖이면 `파티 종류를 선택해주세요.`로 거절한다.
- `update`: 요청에 `partyType`이 없으면 기존 값을 그대로 둔다. `host_name`을 보존하는 방식과 같다.
- 관리자 활동 로그 문구에 종류를 함께 적는다(예: "파티 생성 — [솔로파티] #id 제목").

**B-2. `api/parties.php`(공개 목록 API)**
- 응답에 `partyType`을 추가한다.
- **`detail`은 넣지 않는다.** 10초마다 다시 불러오는 응답이 커지지 않게 하기 위함이다.

**B-3. `app/lib/useParties.ts`**
- 정규화 단계에 `partyType`을 추가한다.

**B-4. `app/lib/data.ts`**
- `Party` 타입에 `partyType?`을 추가한다.

**C-4. [상세페이지 안내] 탭 (신규 편집기)**

위쪽 도구:
- **[다른 파티에서 불러오기]**: 등록된 파티 목록(최근 등록 순, "#id 제목 · 종류 · 날짜")에서 고르면 그 파티의 안내를 그대로 복사한다.
  - 원본 파티에 `detail`이 없으면 원본 종류의 템플릿을 복사한다.
  - 덮어쓰기 전에 확인창을 띄운다.

- 파티 대표 이미지(`imageUrl`) 기능
- 운영 데이터(`api/data/*.json`) 직접 수정 금지, 배포 보호 규칙(`scripts/deploy/*.rsync-filter`)

## 7. 배포 순서

1. **A 작업**(결제·정원)은 단독 PR로 리뷰·병합한 뒤 배포한다(대상 `api`).
2. **B~G 작업 전체**는 함께 배포한다(대상 `all`). B만 먼저 나가면 솔로파티가 매칭파티 안내로 보이게 된다.
3. 배포 후 관리자가 첫 솔로파티를 등록한다. [상세페이지 안내] 탭에서 진행 안내와 사진을 입력한다.

배포는 CLAUDE.md의 절차를 따른다: GitHub Actions `mode=plan` → 운영자 승인 → `mode=deploy`.

## 8. 테스트 및 완료 기준

**A. 정원·결제** (토스 테스트 키 환경. 테스트 환경이 없으면 운영자에게 먼저 확인한다)
- [ ] 남성 정원 15명인 파티에서 13~15번째 카드 결제가 성공하고, 16번째는 결제창이 열리기 전에 막힌다.
- [ ] 정원 8명인 기존 매칭파티에서 9번째가 서버에서 막힌다. 무통장 [결제확인]도 같은 상한으로 막힌다.
- [ ] 승인 뒤 정원 초과가 되는 경우(인원 파일을 임의로 조정해 재현)에 토스 결제가 자동 취소되고, 예약은 생성되지 않으며, 로그가 남는다.
- [ ] 이 경우 쿠폰 사용 이력이 남지 않는다.

**B·C. 관리자**
- [ ] 종류를 고르지 않고 신규 등록하면 저장되지 않는다.
- [ ] 솔로파티를 고르면 [상세페이지 안내]가 빈 상태로 채워지고, 매칭파티를 고르면 지금 내용으로 채워진다.
- [ ] 단계 추가·순서 변경·삭제, 소요시간 줄 편집, 슬롯별 사진 여러 장 추가·순서 변경·삭제·대체 텍스트 입력이 저장 후 그대로 유지된다.
- [ ] [다른 파티에서 불러오기]와 [기본 내용으로 되돌리기]가 확인창을 거쳐 동작한다.
- [ ] 입력 제한을 넘기거나 허용되지 않은 사진 주소를 직접 보내면 서버가 거절한다.
- [ ] 종류 값과 `detail`이 없는 기존 파티를 수정 화면으로 열면 매칭파티와 기본 안내로 보인다. 저장해도 `host_name`, `voting_status`, `status`가 유지된다.
- [ ] 목록의 종류 열과 종류 필터가 월 필터와 함께 동작한다.
- [ ] 375px 모바일에서 편집기를 쓸 수 있다.

**D. 사용자 화면** (모바일 375px, PC 1280px)
- [ ] 메인 종류 탭이 기존 필터와 함께 동작하고, 카드의 종류 배지가 다른 배지와 겹치지 않는다.
- [ ] **`detail`이 없는 매칭파티 상세페이지가 변경 전과 같다**(스크린샷 비교).
- [ ] 내용이 비어 있는 솔로파티 상세에서 진행 안내·소요시간·사진 영역이 빈 여백 없이 사라진다.
- [ ] 관리자가 입력한 단계·사진이 입력한 순서대로 나온다.
- [ ] 페이지를 처음 열 때 솔로파티에 매칭파티 안내가 잠깐 비치지 않는다.
- [ ] 메인 목록 API 응답에 `detail`이 들어 있지 않다.
- [ ] 개인정보처리방침, 환불규정, 가입·프로필 동의문이 D-5대로 바뀌었다.

**E. 현장 운영**
- [ ] 투표 관리 화면의 솔로파티 카드에 [모임종료]와 [종료 취소]만 보이고, 둘 다 예약 상태를 올바르게 바꾼다.
- [ ] 솔로파티에 투표 시작·투표 API를 직접 호출하면 거절되고, 참가자 투표 화면에 솔로파티가 나오지 않는다.
- [ ] 솔로파티의 전날 안내·취소 문자에 "솔로파티"가 나온다.

**공통**
- [ ] `npm run lint`와 `npm run build`가 통과하고, 상세페이지가 1~500번까지 생성된다.
- [ ] 회원가입, 로그인, 장바구니, 쿠폰, 카드 결제, 무통장, 취소요청, 환불승인, 100%환불, 후기 작성을 한 번씩 확인한다.

## 9. 남은 확인 사항 (운영자)

아래는 법적 문서 문구에 관한 것이다. 개발과 동시에 정하면 된다.
1. **개인정보처리방침 시행일.** 처리방침을 바꾸면 바뀐 내용과 시행일을 알 수 있게 공개하는 것이 원칙이라, 부칙 시행일을 실제 배포일로 바꾸는 안을 넣었다. 공지 기간 등 정확한 절차와, 기존 회원에게 다시 동의를 받아야 하는지는 전문가 확인을 권장한다(이 명세서는 법률 자문이 아니다).
2. **환불규정 30행** "파티 매칭 확정 이후"를 "파티 참가 확정 이후"로 바꿔도 원래 의도와 같은지
3. **환불규정 153행** "매칭 파트너의 노쇼"를 "다른 참가자의 노쇼"로 넓혀도 되는지(솔로파티에도 적용됨)
